## 阅读顺序

0001 地基 → 0002 打包试验 → 0003 资料库规划 → 0004 P3 边界 → 0005 P3 实现 → 0006 全功能插件化 → 0007 插件 npm 化 → 0008 运行时插件 → 0009 分层清理 → 0010 构建期插件自动发现 → 0011 插件宿主阶段一 → 0012 运行时插件 v2 → 0013 插件数据归属 → 0014 首页块与构建期权限边界。

- **0001 地基**：单仓 + 全栈 TS，core 零 UI 零平台。
- **0002 打包试验**：一次性 Electron/Capacitor 壳，验证"一份 dist 多壳"。
- **0003 资料库规划**：资产层、单词库、转换/连接器只定边界。
- **0004 P3 边界**：插件数据互访、独占页面、UI 三档。
- **0005 P3 实现**：落地取舍与故意留的边界。
- **0006 全功能插件化**：为什么打印与数据管理留在 core。
- **0007 插件 npm 化**：取消运行时加载，回到构建期。
- **0008 运行时插件**：新增主进程加载器、五方法契约、CLI；构建期 UI 插件仍保留。
- **0009 分层清理**：core 只留原语/纸面契约；共享领域进 domain；单插件逻辑进插件包。
- **0010 构建期插件自动发现**：Vite glob 扫描 plugins/*，删目录后直接构建。
- **0011 插件宿主阶段一**：绑 0.0.0.0，LAN 403，数据层未接。
- **0012 运行时插件 v2**：页面/主题/数据/扫描 + PWA 客户端；数据仍在本机。
- **0013 插件数据归属**：禁用插件后数据契约与首页/番茄/扫描一起降级。
- **0014 首页块与权限边界**：首页全部插件块 + 拖拽；构建期插件走授权 store。

读完这 14 篇能回答"为什么是这个架构"：在单人维护、离线优先、纸是主输入端三个约束下，
每一步都用最小改动保住数据不变量与可替换性。
