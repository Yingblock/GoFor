# GoFor 路线图 v0.3

> 基于 2026-xx 反馈重排。**估算单位改为「对话轮数（轮）」，不再按工时/周数排期**——
> 开发由 Agent 驱动，人时不再是有意义的单位。
> **1 轮** = 一次请求内能完成、能自检（类型 + 单测，必要时 e2e）的改动，量级约等于原来的
> 约等于原来一个中等 issue。**一个任务超过 3 轮就必须拆**；一个阶段 20–40 轮是正常的（如 P3 拆
> `P3a`/`P3b`）。
> 轮数是量级估计，不是承诺；真实轮数取决于需求变化与返工。
> 原则：**每一阶段结束时，产品都能被你自己真实使用。**
> v0.3 变更：错题本改「扫描 + 混排」；去门禁；平台定为 Windows/Android 一级 + PWA 优先；确立「纸张优先」设计律（见 DESIGN.md §1）。
> v0.3.1 变更（2026-10-30）：估算单位工时 → 对话轮数；P0–P2 的工时只作历史记录。

### P3 的扩展契约（2026-10-30 用户确认，✅ 已实现，取舍见 `DECISIONS/0005`）

3.1–3.8 回答的是"插件怎么进来"，没回答"插件之间怎么协作、能不能改界面"。补三条，
边界与"为什么"记在 `DECISIONS/0004-plugin-extension-boundaries.md`。

1. **插件之间只能通过契约交换数据（3.9）**。共享数据一律走
   `DataContract { id, version, query(input) → plain JSON, revision() }`，manifest 里声明
   `provides.data` / `consumes.data`；core 的数据也做成内置 provider，
   **插件与 core 走同一条路**。直接互读 `pluginData` 是禁止的：对方被禁用/卸载后读者会
   静默读到空，变成"周报显示本周 0 分钟"这种看不出来的错——与本项目"打印时固化坐标清单"
   是同一条原则。事件总线只广播"某类数据变了"，载荷只放 id，不放快照。
2. **独占页面（3.10）**。`screen` 贡献项带 `layout`（内容区内边距 / 占满）与 `chrome`
   （保留外壳 / 连 header 一起让出），懒加载以免挤进首屏单 chunk（现在主 bundle 756KB + 扫描懒加载 chunk 423KB）。
   因为当前导航是组件 state、没有 URL，同时补一个最小 hash 路由 `#/s/<id>`：
   刷新保持、后退有效、`gofor://` 能指到插件页。
3. **UI 扩展分三档（3.11），不给任意 DOM**。档 1 主题 token、档 2 命名插槽 + shell 变体、
   档 3 作用域 CSS。三档都是"在宿主给的边界里改"，不是"接管外壳"。理由是这个项目有三条
   很容易被美化插件破坏的承重契约：`.screen-only` / `.print-root` 分离（P1 打白纸事故）、
   深色下纸面固定黑字白底、360px 无横向溢出 + 约 150 项 e2e 断言。任意 DOM 还导致卸载后
   无法还原、出事无法定位是哪个插件干的。

**落地位置**：契约 `packages/plugin-api`（新建）；依赖解析与版本协商
`packages/core/src/plugin`（纯逻辑，可单测）；内置 provider `packages/store`；
路由 / 插槽 / 主题 `apps/web/src/plugins/`。`App.tsx` 的 switch 与 `nav.ts` 的 union
是这两项的前置改造（见 3.3）。

**拆分建议**：`P3a` 契约与可验证骨架 = 3.1 + 3.2 + 3.12 + 3.9 + 3.4 + 3.5（16 轮，
纯收益：插件能装、能读、能进备份、能占一个页面、命令面板全量）；
`P3b` 迁移与内容 = 3.3 + 3.7 + 3.10 + 3.11 + 3.6 + 3.8（14 轮，纯重构）。
P3a 做完就能验"加插件不改核心"；P3b 风险高得多，不该和后端契约混在一个里程碑里。

## 2.5 首页：统计缩成小字 + 热力图（用户要求，暂不实现）

用户原话：「首页统计字数部分改为小字，剩余画幅放热力图，支持周/月/年查看」。

现状问题：首页四张 `StatCard` 占了一行宽度，数字大、信息密度低；真正想知道的是
「这段时间到底学了多少、哪几天断了」，这是热力图能回答的，统计卡片不能。

规划（不在本轮实现）：

| 项 | 设计 |
|---|---|
| 统计区 | 四张卡片改成一行小字摘要（`今日 42 分 · 连续 6 天 · 待办 3 · 作业 2/5`），高度 ≤ 28px |
| 热力图 | 占满剩余画幅；格子 = 一天，颜色深浅 = 当日学习分钟数（`sessions` 聚合，不新增记录） |
| 时间范围 | 周 / 月 / 年三档切换；周视图 1×7，月视图 5–6×7，年视图 53×7（GitHub 风格） |
| 空数据 | 没记录的格子用最浅底色，不画"0"；悬停/聚焦显示「日期 · N 分钟 · M 条记录」 |
| 可访问性 | 每格 `aria-label` 带日期与分钟；键盘可逐格浏览；`prefers-reduced-motion` 下不做过渡 |
| 数据来源 | 只用 `sessions`（番茄钟 + 纸面回填），不做"打卡/心情"叠加，避免两个口径互相污染 |
| 验收 | 两个月真实数据下，能一眼看出断档日；年视图在 360px 宽仍不出框（横向滚动或按季度分块） |

依赖：无新增依赖（手写网格 + CSS 变量上色）。

## 3. 打印模板库规格（回应"概念需要进一步详细"）

> 本节是 P1 的模板规格。现行区块、版式与时间记录模型见 `docs/DESIGN.md` §4 / §6，冲突时以 DESIGN 为准。

模板不是"一张写死的 HTML"，而是 **数据绑定 + 声明式版式 + 纸张规格**。

```ts
interface PrintTemplate {
  id: string;
  name: string;
  // 9 种，见 core/print/paper.ts；B5 分 JIS(182×257) 与 ISO(176×250)
  paper: 'A4' | 'A5' | 'A6' | 'B5' | 'B5-ISO' | 'B6' | 'letter' | 'index-card' | 'sticker-50x30';
  orientation: 'portrait' | 'landscape';
  margin: { top: number; right: number; bottom: number; left: number }; // mm
  columns?: number;                       // 分栏（口袋卡用 2–4 栏）
  blocks: Block[];                        // 每个 block 带 span/rows 等字段，kind 见下方 BlockKind
  bindings: Record<string, DataSelector>; // 名字 -> 数据来源
}

// 区块类型以 packages/core/src/print/blocks.ts 的 BLOCK_KINDS 为准
type BlockKind =
  | 'title' | 'hintLine' | 'footer' | 'pageBreak' | 'progressDots' | 'qrcode'
  | 'checkboxList' | 'checkboxGrid' | 'ratingGrid' | 'habitRow'   // 勾选/打分/打卡行
  | 'timeLog' | 'schedule' | 'timestamp'                          // 时间登记 / 预印课表 / 打印时刻
  | 'table' | 'slots' | 'linedBox';                               // 表格 / 三小格 / 手写区
```

**纸上的时间只记一种**：`timeLog`（写做了什么 + 起止，按上午/下午/晚上分栏消除歧义），
在校时段用 `schedule` 预印课表 + 例外登记（只圈掉没学的）。
已撤回：专注格 `focusGrid`（涂格记时长）——纸面成本高于收益，见 `docs/LATER.md`「专注格」；
配置里的 `print.focusGrid` / `focus.unit` 是它的残留，不要据此扩展设计。

两种入口（纸面 `timeLog`、番茄钟）都产出同一种 `StudySession`，统计与周报只写一套。

渲染链路：

```
Template + Data → React 组件树 → HTML + @page CSS → window.print()
                                          └→ 同时输出 print_meta.json（每个 checkbox 的归一化坐标）
```

**关键设计：渲染时同步产出坐标元数据。**
这就是 P2 回填能成立的原因——扫描时不需要通用 OCR，只需要在已知坐标的小窗口里判断"有没有墨迹"。

**v1 模板清单**：

| 模板 | 纸张 | 用途 | 必备元素 |
|---|---|---|---|
| 今日清单 | A5 / A4 | 每天一张，贴在书桌上 | 任务格 + 时间登记 + QR + 书写提示 |
| 周计划 | A4 横 | 一周任务 + 考试 + 打卡格 | 7 天格 + 打卡格 + 时间登记 + QR |
| 课程表 | A4 | 单双周全显示，作业区域留白 | 表格 + 留白写字区 + QR |
| 打卡卡 | A5 / 便利贴 | 21 格习惯追踪 | 勾选格 + QR |
| 口袋卡 | index-card | 公式 / 单词 / 待办，可裁可订 | 分栏 + 无 QR（尺寸太小） |
| 考试倒计时牌 | A4 | 手写大字，贴墙上 | 大字留白 + 进度点 |
| **打印校准页** | 任意 | **排查打印机缩放/边距/裁剪**，每台打印机打一次 | 10mm 刻度 + 四角定位标 + 边框 |

**设计要点**：所有"每日/每周"模板都必须自包含——**不看 App 也知道怎么填**，因为在学校打不开 App。

**口袋卡为什么不用单独排期**：它就是 `paper: 'index-card'` + `columns: 2`。模板引擎做好后，每个新模板约 1 轮（主要是调版式）。

## 4. 启动阻力最小化 规格（回应"设计上需要详细考虑"）

目标是让"开始专注"的物理成本接近 1 次点击。

1. **主界面第一屏就是开始按钮**，点击 = 开始「上次的科目 + 上次的时长」。不需要进入任何菜单。
2. **长按**按钮 = 换科目 / 时长。
3. **最近 5 个任务 chip**，直接点即开始绑定该任务。
4. **从作业清单任一项直接"开一个番茄"**，不在番茄钟页面也能开。
5. **一键多入口**：桌面图标、Android 小组件、通知栏常驻、锁屏、快捷键 `Space`。
6. **默认时长按高中生节奏**：45+10（课时）而非 25。可设 25/45/90。
7. **"只做第一个番茄"的心理契约**：开始前一句话，降低启动门槛。
8. **中途退出不阻塞**：轻提示"会话还在，回来继续"，而不是弹窗确认。
9. **零配置**：第一次打开就给一套默认值，不让用户先做设置向导。

反例（要避免的）：打开 App → 选科目 → 选时长 → 选任务 → 点开始 = 4 次交互，用户会放弃。

## 5. 中国课表 模型策略（回应"有没有现有好用的 strategy"）

**答案：用 iCalendar 的 RRULE 思想，不要自创。**

| 中国现实 | 用标准怎么表达 |
|---|---|
| 每周固定 | `FREQ=WEEKLY;BYDAY=MO;COUNT=20` |
| **单双周** | `FREQ=WEEKLY;INTERVAL=2;BYDAY=MO` |
| **连堂**（两节连上） | `span: 2`（占两个 period，不是两条规则） |
| **走班 / 选修** | `group: 'A'`，学生只订阅自己选的组 |
| **调课** | 主规则 + `Override { date, action: 'move'|'cancel'|'replace', payload }` |
| **特殊周** | `WeekPattern`：`normal` / `exam` / `holiday` / `vacation`，每学期一个日期→模式映射 |
| **考试排期** | 单独实体，不塞进课表 |

数据模型：

```ts
Course      { id, name, teacher, location, color }
Rule        { courseId, byDay, interval, startPeriod, span, group, termId }
Override    { ruleId, date, action, payload }
WeekPattern { termId, dateRange, pattern }
```

**关键：`Occurrence` 是计算出来的，不落库。** 落库会在每次改规则时产生大量脏数据。

**导入路径（按优先级）**：
1. **手工编辑**（必须有，且要好用）
2. **ICS 导入**（如果学校/自己用日历）
3. **拍照识别课表**（这个 OCR 反而简单：固定表格、印刷体、字号大）
4. ❌ **教务系统爬虫**——不做。验证码、登录态、账号封禁、各校差异，是个无底洞。

**要不要插件化课表？** 不需要。课表是"有明确边界的成熟问题"，插件化只会增加复杂度。
真正该做成可配置的是 **Period 表（作息时间）和 WeekPattern**——每个学校作息不一样，这是纯数据配置，不是代码。

**参考产品**：WakeUp 课程表（单双周/调课做得最完整）、ClassUp、超级课程表。学它们的数据模型，别学它们的爬虫。

## 6. 独立应用 + 私服：架构约束（回应补充问题）

你的分发模式（源码 + 产物在 GitHub，用户自建服务器）对架构有 6 条硬约束：

### 6.1 零后端必须完整可用

服务端是**可选增强件**，不是地基。断网、无服务器、永不联网时，P1–P6 的所有功能必须 100% 正常。这一条要写进测试用例。

### 6.2 服务器地址是一个设置项

设置里一个输入框："服务器地址"。填了连，空白就是纯离线。**不要做设备-账号强绑定**，否则同学没法用。

### 6.3 私服用 SQLite，不用 Postgres

单用户/几个人的私服：SQLite 单文件 + 定时备份，运维量接近 0；Postgres 要容器、要升级、要调参。**P7 的 7.1 我已经改成 SQLite。**
如果以后真需要多用户，SQLite → Postgres 的迁移成本远小于你现在维护 PG 的成本。

### 6.4 服务器只存加密 blob（强烈推荐）

同步不要做"服务端懂你的数据模型"，改成：

```
客户端 → 本地导出为加密 vault（如 age / libsodium）→ 上传密文 blob
服务器 → 只负责「谁的 vault、第几版、多大、哈希」→ 存储和版本管理
```

好处：
- 服务器实现量砍掉一半以上（不用写 migration、不用管 schema 兼容）
- 私服主人的服务器被攻破也不泄露你的错题和情绪日记
- 数据模型怎么改都不影响服务端
- 冲突处理全在客户端（你本来就要写）

代价：服务端无法做搜索/统计/聚合。但私服场景本来也不需要。

### 6.5 必须有版本握手

client 和 server 独立升级，私服用户可能一台跑旧 server、一台跑新 client。

```
GET /api/version → { apiVersion: 3, minClient: 2, minServer: 2 }
```
不兼容时**明确报错并给升级指引**，而不是诡异崩溃。

### 6.6 分发渠道与平台

| 渠道 | 覆盖 | 注意 |
|---|---|---|
| **PWA（主渠道）** | **Windows / Linux / macOS / 手机浏览器** | 一个 URL 即用、自动更新。**P1 就能用，Windows 打印直接走 `window.print()`** |
| Android APK | Android 原生能力 | Capacitor 打包；**签名密钥务必另处备份**，丢了无法覆盖升级 |
| Tauri 桌面版 | 可选的本地能力 | 推迟，见下 |

**明确不做**：

- ❌ Electron（150MB+、吃内存，学生电脑不友好）
- ❌ 鸿蒙（NEXT 不兼容 APK、侧载受限、文档不成熟）
- ❌ Windows 专用桌面版（PWA 已覆盖 90% 需求，省 60–80h）

**Tauri 值得做的最小触发条件**（任一条成立再动手）：
1. 需要读本地文件系统（批量导入 PDF/试卷）
2. 需要全局快捷键 / 托盘常驻 / 开机自启
3. 需要桌面端活动窗口与空闲时间采集

### 6.7 关于"现在先别写服务器"

P1–P6 的多端需求，用 **导出 JSON + Syncthing / 网盘** 就能满足，成本 ≈ 0，能省下 180 小时。
**把 P7 推到"你真的有两台设备且天天同步"之后再动手。** 很可能到高三你都不需要它。

5. P4 的扫描链路 → 退化为"手动裁剪 + 全贴图"（省约 7 轮；**混排方案下这仍然可用**，只是全变图片）
6. P4 的 OCR → 全手动（省约 3 轮）
7. P2 的笔迹识别 → 退化为"扫码定日 + 手动回填"（省约 4 轮，仍保留二维码的价值）

**唯一不能砍的是 P1。** 没有 P1 就没有产品。

> 注意第 5 条：**混排方案的最大好处之一就是它可逐级降级**——从"扫描+OCR+混排"一路退到"拍照+全贴图"，产品始终成立。这是 v0.2 全 OCR 方案做不到的。
