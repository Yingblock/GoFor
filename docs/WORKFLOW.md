# 进度管理方法

> 目标：**用最少的维护成本，保证 8 个月后（甚至中断半年后）回到项目还能立刻继续。**

---

## 0. 一句话版本

> **GitHub Projects 看板 + Milestone = 阶段 + Issue ≤ 8 小时 + 每周日 30 分钟复盘 + `docs/STATE.md` 单点真相源。**

不要引入 Notion / Linear / 飞书。**多一个要维护的地方，就多一个会腐烂的地方。** 代码已经在 GitHub 上，管理就应该长在同一个地方。

---

## 1. 四层结构

| 层 | 载体 | 粒度 | 谁在变 |
|---|---|---|---|
| 战略 | `docs/ROADMAP.md` | 阶段（P0–P8） | 几乎不变 |
| 战术 | **GitHub Milestone** | 一个阶段 = 一个 milestone | 每 1–2 个月 |
| 执行 | **GitHub Issue** | 2–8 小时/个 | 每周 |
| 当下 | **`docs/STATE.md`** | 现在在哪、下一步做什么 | 每次收工 |

**Milestone 同时只开一个。** 看板里只允许一个阶段处于"进行中"，其余全部 backlog。
这是单人项目最重要的纪律——**防止同时在五个阶段之间打转**。

---

## 2. 看板设置（GitHub Projects，5 分钟搞定）

列（Status）：`Backlog → Ready → In Progress → Review → Done`

- `Ready`：需求已明确、能立刻动手 → **每周日从 Backlog 里挑 3–5 个放进来**
- `In Progress`：**WIP 上限 = 1**（最多 2）。单人开发输给多任务切换，不输给产出速度
- `Done`：有测试、能跑、`git push` 了

### Labels

| 标签 | 含义 |
|---|---|
| `P0`…`P7` | 属于哪个阶段 |
| `size:S` / `M` / `L` | 2h / 4h / 8h。**超过 8h 必须拆** |
| `type:feat` / `fix` / `chore` / `docs` / `spike` | 类型 |
| `gate:real-use` | 阶段验收项（必须真的用过才算完） |
| `blocked` | 卡住，需要写清楚卡在哪 |

### 为什么"超过 8h 必须拆"

20 hrs/week ≈ 每周 2.5 个 8h 任务。**一个 20h 的 issue 会让你两周看不到进度**，然后失去动力。
Issue 小到"一次坐下能干完"，是维持 8 个月动力的关键。

---

## 3. 每周节奏（真正的核心机制）

### 周日晚上 30 分钟（固定）

1. 把本周做完的 issue 拖到 `Done`（没做完的写一句"卡在哪"）
2. 在 `docs/DEVLOG.md` 记一行：`第 N 周 | 计划 Xh | 实际 Yh | 完成 issue 数 | 本周我自己用了吗`
3. 从 Backlog 挑下周的 3–5 个 issue 到 `Ready`
4. **更新 `docs/STATE.md`**：现在在哪、下一步是什么、什么是坏的

### 每次坐下开工 5 分钟

1. 读 `docs/STATE.md`
2. 读当前 issue 的验收标准
3. 确认 `pnpm test` 是绿的（不是的话先修，别叠加）

### 每次收工 3 分钟

1. commit（哪怕没做完，用 `wip:` 前缀）
2. 更新 `docs/STATE.md` 的"下一步做什么"
3. 如果做了架构决策，写一条 `docs/DECISIONS/00xx-*.md`

---

## 4. 三条真正决定生死的纪律

### ① 「真实使用」才是进度条

代码量不是进度，**你自己连续用它的天数才是**。
每个 phase 的 milestone 里必须有一个 `gate:real-use` issue，验收标准是行为，不是功能：

- P1：连续两周每天打勾，且真的打印了 ≥5 张纸
- P2：周五晚上能把一周的纸一次扫完
- P4：一周的错题真的排进复习且你刷了

**没过这个 gate 就不开下一个 phase。** 这是唯一能防止"做了很多但没人用"的机制。

### ② 停车场（`docs/LATER.md`）

你会有源源不断的新想法——这很正常，而且是好事。**但它们不能进入当前阶段。**

> 任何新想法 → 立刻写进 `docs/LATER.md`，不做任何实现。
> 每周日复盘时允许"认领"最多 1 个。

没有停车场，你的 P1 会变成"顺便也做了笔记和云同步"的 P1，然后永远做不完。

### ③ 中断恢复仪式

你会因为考试停两周、因为高三停半年。**恢复项目的能力比开发能力更重要。**

`docs/STATE.md` 就是为此存在的。它必须能让"半年后的你"在 10 分钟内搞清楚：

```md
## 现在在哪
## 下一步做什么（最多 3 条）
## 什么坏了 / 什么没做完
## 上次做到哪、怎么跑起来
```

---

## 4.5 长任务不要占着主线程

`pnpm build`、`pnpm e2e`、打包、下载依赖都可能跑几分钟到一个小时。
这类任务一律交给子代理或后台作业，主线程继续做别的事。

判据很简单：**预计超过 1 分钟，就不该在主线程里等。**
详见 `AGENTS.md` §0（硬规则，优先级高于本文档）。

## 5. 与 AI 协作时的额外纪律

你会大量用 AI 写代码，这带来一个特有风险：**代码你越来越不熟，半年后看不懂。**

对策：

| 做法 | 作用 |
|---|---|
| `AGENTS.md` 放仓库根目录 | 每次让 AI 干活前，它自动读到约定（技术栈、目录、禁用项、测试命令） |
| `docs/DECISIONS/` 记录"为什么" | AI 生成的代码通常有"是什么"没有"为什么"。ADR 补上这一半 |
| 每个 issue 结束时 `pnpm test` 必须绿 | AI 最容易留下"看起来对但没接线"的代码 |
| 关键域逻辑（时间、SRS、同步）**自己写** | 这些出错时的调试成本远高于手写成本 |
| commit message 写"为什么" | `feat(pomodoro): 用时间戳而非 tick 累加，避免后台节流导致漂移` |

**一个可执行的判定**：如果你无法在 3 分钟内口述某个文件在做什么，那它就该重写或加注释。

---

## 6. Git 约定

- **trunk-based**：直接推 `main`，功能大到要分支时用 `feat/xxx`，合并后删掉
- **Conventional Commits**：`feat:` `fix:` `chore:` `docs:` `refactor:` `test:`
- **每个 phase 结束打 tag**：`v0.1-p1-offline-mvp`、`v0.2-p2-paper-loop`…… tag 就是你回滚的锚点
- **不追求完美 commit**：一次 commit 只做一件事就够，别 amend 到天荒地老

---

## 7. 时间预算（20 hrs/week 怎么分配）

| 用途 | 比例 | 每周 |
|---|---|---|
| 主要 issue | 60% | 12h |
| 打磨真实使用中发现的坑 | 20% | 4h |
| 学新东西 / spike | 15% | 3h |
| 复盘与文档 | 5% | 1h |

**那 4h 的"坑"不可省。** 它是把"能跑"变成"我愿意用"的唯一环节，也是很多个人项目死掉的地方——他们只造不加打磨。

---

## 8. 里程碑日历（倒排）

| 时间 | 目标 |
|---|---|
| 第 2 周末 | P0 完成，手机上能装上 |
| 第 10 周末 | **P1 完成，开始每天用它** |
| 第 16 周末 | P2 完成，纸→数字闭环打通 |
| 第 21 周末 | P3 完成，架构稳定，可以长期放着 |
| 第 30 周末 | P4 完成，错题复习跑起来 |
| 高三开始前 | 至少到 P4，且项目处于"可安全搁置"状态 |

> **"可安全搁置"的标准**：所有测试绿、README 能让人从零跑起来、STATE.md 是最新的、没有半成品分支。这是你高三前最重要的交付物——比任何功能都重要。
