# 工作流

> 一句话：用最少的维护成本，保证中断半年后回来还能立刻继续。

## 1 四层结构与看板

| 层 | 载体 | 粒度 | 谁在变 |
|---|---|---|---|
| 战略 | `docs/ROADMAP.md` | 阶段（P0–P8） | 几乎不变 |
| 战术 | GitHub Milestone | 一个阶段 = 一个 milestone | 每 1–2 个月 |
| 执行 | GitHub Issue | ≤3 轮/个，超过 3 轮必须拆 | 每轮 |
| 当下 | `docs/STATE.md` | 现在在哪、下一步做什么 | 每次收工 |

- **估算单位是「对话轮数」**：1 轮 = 一次请求内能完成、能自检（类型 + 单测，必要时 e2e）的改动；排期、砍功能、复盘都按轮数算。
- **Milestone 同时只开一个，WIP = 1（最多 2）**：只允许一个阶段"进行中"，其余全是 backlog——单人开发输给多任务切换，不输给产出速度。
- 看板列 `Backlog → Ready → In Progress → Review → Done`；`Ready` = 需求已明确、能立刻动手（每周日从 Backlog 挑 3–5 个进来），`Done` = 有测试、能跑、已 push。
- 不引入 Notion / Linear / 飞书：多一个要维护的地方，就多一个会腐烂的地方。

### Labels

| 标签 | 含义 |
|---|---|
| `P0`…`P7` | 属于哪个阶段 |
| `size:S` / `M` / `L` | 1 轮 / 2 轮 / 3 轮；**超过 3 轮必须拆** |
| `type:feat` / `fix` / `chore` / `docs` / `spike` | 类型 |
| `gate:real-use` | 阶段验收项，必须真的用过才算完 |
| `blocked` | 卡住，写清楚卡在哪 |

- **为什么必须拆到 3 轮内**：5 轮以上的 issue 会让你连续几轮看不到可验收的进度，出问题也难定位是哪一步坏的。

## 2 每周节奏

### 周日晚上 30 分钟（固定）

1. 把本周做完的 issue 拖到 `Done`，没做完的写一句"卡在哪"。
2. 在 `docs/STATE.md`「最近一次更新」记一行：`第 N 周 | 计划 X 轮 | 实际 Y 轮 | 完成 issue 数 | 本周我自己用了吗`。
3. 从 Backlog 挑下周的 3–5 个 issue 到 `Ready`。
4. 更新 `docs/STATE.md`：现在在哪、下一步是什么、什么是坏的。

### 坐下开工 5 分钟

1. 读 `docs/STATE.md`——省掉重新回忆项目的成本。
2. 读当前 issue 的验收标准——避免做完才发现做偏。
3. 确认 `pnpm test` 是绿的——红的上面不要叠新改动。

### 收工 3 分钟

1. commit（没做完也用 `wip:` 前缀）——进度要留痕。
2. 更新 `docs/STATE.md` 的"下一步做什么"——给中断后的自己留接续点。
3. 做了架构决策就写一条 `docs/DECISIONS/00xx-*.md`——AI 代码只有"是什么"，缺"为什么"。

## 3 并行与子代理

**判据**：预计超过 60 秒的命令不进主线程；手上 ≥2 件互不依赖的事必须同时开；判不准按长任务处理（默认从严）。

### 决策表

| 场景 | 正确做法 |
|---|---|
| 单条命令预计 > 60s（build / e2e / install / gradle / 截图 / 下载） | `run_in_background: true` 起后台作业，立刻继续做别的事 |
| 要"等某个条件成立"（文件出现、端口就绪、构建完成） | 子代理内部轮询，主线完全不管 |
| 多步骤且中间可能失败、需诊断重试 | 子代理（它能自己修再报） |
| ≥ 2 件互不依赖的工作 | 同一轮里发出多个子代理，不要一个个来 |
| 打包 / 发 Release / 全量 verify | 一律子代理，不要用后台作业顶替——后台作业仍占着主 session 的回合 |
| 预计 < 60s 的查询、读文件、小改动 | 主 session 直接做 |
| 不确定要多久 | 按长任务处理 |

### 明确禁止

- 在主 session 里 `sleep 120` 等下载。
- 一条命令串多个长步骤（`build && e2e && 截图`）。
- "等结果回来再继续"——结果应由子代理或后台作业通知回来。
- 反复 `job_output` 轮询同一个作业。
- 为省事把长任务留在主线，理由是"它应该很快"。

### 自检 4 问

- 调用 bash 前：这会不会超过 60 秒？会 → 后台或子代理。
- 开始一项子任务前：还有别的能同时做的吗？有 → 现在就并行发出去。
- 这是"苦力"吗（构建、上传、批量验证、截图、e2e、打包、全量 verify）？是 → 子代理，不是我。
- 命令里出现 `e2e` / `verify` / `build.sh` / `gradle` / 下载？出现 → 绝不主线跑。

### 本仓库实测耗时

| 操作 | 实测 |
|---|---|
| `pnpm test` | 0.3 s |
| `pnpm typecheck` | 2–5 s |
| `pnpm build` | 1–2 s |
| `pnpm e2e`（起浏览器 + PDF，需 plugin-host） | 15–30 s |
| Playwright 截图脚本 | 10–20 s |
| 首次安装 Playwright 浏览器 | 1 m 31 s |
| `pnpm install`（新增依赖） | 10 s – 1 m |
| Android **首次** gradle 构建 | 29 m 45 s |
| Android **增量**构建 | 8 s – 5 min |
| Electron 包重建 | 1–3 min |

> 前四项单独看很快，但常被串在一起且首次会下载东西；一条命令里出现两个以上就按长任务处理。

**委派模板**（目标 / 环境 / 允许 / 禁止 / 超时兜底 / 报告）见 `AGENTS.md` §1，按它填写，不要自创格式。

## 4 三条纪律

### ① 真实使用才是进度条

- 代码量不是进度，**你连续用它的天数才是**：每个 milestone 必须有 `gate:real-use` issue，验收标准写行为不写功能（P1 连续两周每天打勾且真打印 ≥5 张纸；P2 周五晚能把一周的纸一次扫完；P4 一周错题真排进复习且你刷了）。
- **没过 gate 不开下一个 phase**——这是唯一能防止"做了很多但没人用"的机制。

### ② 停车场 `docs/LATER.md`

- 任何新想法立刻写进 `docs/LATER.md`，不做实现；每周日复盘允许认领最多 1 个——没有停车场，P1 会变成"顺便也做了笔记和云同步"的 P1，然后永远做不完。

### ③ 中断恢复仪式

- 你会因考试停两周、因高三停半年；**恢复项目的能力比开发能力更重要**。`docs/STATE.md` 必须让"半年后的你"10 分钟内看懂，必备章节：

```md
## 现在在哪
## 下一步做什么
## 什么坏了 / 什么没做完
## 怎么跑起来
```

## 5 CI 与提交

- `.github/workflows/verify.yml` 在 push `main`、每个 PR、手动触发时跑 `pnpm verify` **四连**：typecheck + test + build + e2e。
- e2e 走真实浏览器并自起 `127.0.0.1:4173` 的 preview——IndexedDB、打印 CSS、全屏遮罩在 Node 里测不出来。
- **红 = 阻塞合并，不绿不合并**：任何一环挂了都算这次改动有问题，先在本地跑 `pnpm verify` 复现（本地与 CI 同一条命令），不要"先合再修"。
- CI 只做校验：不部署、不发 release、不读 secrets。
- **trunk-based + Conventional Commits**：直接推 `main`，功能大到要分支时用 `feat/xxx` 并及时删；commit 用 `feat:` `fix:` `chore:` `docs:` `refactor:` `test:`，一次只做一件事。
- **每个 phase 结束打 tag**（`v0.1-p1-offline-mvp`、`v0.2-p2-paper-loop`……）：tag 是回滚锚点。
- 测试与类型的具体要求、ADR 流程见 `STANDARD.md`，本文不复述。

## 6 轮数预算与里程碑检查点

| 用途 | 比例 | 说明 |
|---|---|---|
| 主要 issue | 60% | 推进里程碑 |
| 打磨真实使用中发现的坑 | 20% | 修 bug、补体验 |
| 学新东西 / spike | 15% | 不确定的技术先探 |
| 复盘与文档 | 5% | STATE / ROADMAP / ADR |

- **那 20% 的"坑"不可省**：它是把"能跑"变成"我愿意用"的唯一环节，也是个人项目最常见的死法。

累计轮数从 P3 起算（P0–P2 已完成不计，见 `ROADMAP.md` §1）：

| 累计轮数 | 目标 |
|---|---|
| 30 | P3 完成，架构稳定，可以长期放着 |
| 72 | P4 完成，错题复习跑起来 |
| 97 | P5 完成（可选，要非常克制） |
| — | 高三开始前至少到 P4，且项目处于"可安全搁置"状态 |

- **"可安全搁置"**：测试全绿、README 能让人从零跑起来、`STATE.md` 最新、没有半成品分支——这是高三前最重要的交付物。

## 7 与 AI 协作的注意事项

- **关键域逻辑自己写**（时间、SRS、同步）：出错后的调试成本远高于手写成本，也最容易被"看起来对"的 AI 代码毁掉。
- **commit message 写"为什么"**：`feat(pomodoro): 用时间戳而非 tick 累加，避免后台节流导致漂移`——半年后只有它能解释这段代码。
- **3 分钟口述检验**：如果你无法在 3 分钟内口述某个文件在做什么，那它就该重写或加注释。
